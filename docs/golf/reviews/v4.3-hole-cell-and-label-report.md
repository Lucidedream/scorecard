# v4.3 hole-cell fix and label report

## Outcome

Items 1 and 2 of this brief were already implemented and tested in the working tree
before this task started (the brief's claim that no prior edits existed was wrong; the
coordinator confirmed this after I verified the code against the spec). Only item 3
(the label rename and its width consequence) required new work.

### Item 1 — HOLE now reads the seeded score

`src/golf/GolfScoringDisplay.h` (new file) defines `GolfScoringHoleDisplay` and the
`golfScoringHoleDisplay(round, score, hole)` helper, which is the single place that
decides whether a hole's displayed score is seeded (`seedGolfHoleAtPar`, unchanged
precondition `par >= 3` and hole untouched) or the stored counters. Both
`GolfScoringActivity::drawCounters` and `::drawTotals`
(`src/activities/golf/GolfScoringActivity.cpp:589, 656`) call this one helper — neither
holds its own copy of the preseed condition. `handleConfirm` also reads
`display.seeded` instead of re-deriving it. On an untouched par 3/4/5, `display.score`
equals `par` (seeded `2 + 2 + (par-2)`), so `HOLE` reads `E`; on a par-free hole nothing
is seeded and `HOLE` falls back to the unsigned stroke count per §18.1.

### Item 2 — hole number gets breathing room

`src/activities/golf/GolfUiLayout.h:14-15` adds `SCORING_HOLE_DIGIT_MAX_HEIGHT = 48`
(was an inline `58`) and `SCORING_HOLE_DIGIT_RULE_GAP = 12` (was an inline `4`), read by
the new `scoringHoleDigitHeight()` / `scoringHoleDigitTop()` helpers
(`GolfUiLayout.h:119-125`) that `drawHoleBand` now calls
(`GolfScoringActivity.cpp:498-500`). The band's own height and everything below it are
unchanged; only the digit shrinks and lifts off the rule.

### Item 3 — "SCORE ZONE" becomes "TO SCORE ZONE"

`STR_GOLF_SCORING_ZONE` in `lib/I18n/translations/english.yaml` is now `"TO SCORE
ZONE"`; i18n regenerated with `.venv/bin/python scripts/gen_i18n.py
lib/I18n/translations lib/I18n/` (generated files not part of the handoff).

**Width measurement.** Measured directly through `EpdFontFamily::getTextDimensions()`
against the built-in `ubuntu_10_bold` face (the same font/style `drawCounters` uses for
labels): `"SCORE ZONE"` = 129 px, `"TO SCORE ZONE"` = 162 px.

Reconstructing the counter row's exact production geometry (`padding =
minValue(P, rect.width/8)`; digit centered at `rect.x + rect.width/2`; digit width from
`golfDrawLargeNumber`'s `height * 11/20` formula) for the scoring-zone row, **focused**,
in **portrait** (480 px wide — the narrowest orientation, and therefore the tightest
case):

| `out100` digits | digit height | space between label and digit, `P=20` (old) | `P=16` (new) |
| --- | --- | --- | --- |
| 1 (normal play) | 100 px | 193 px | 197 px |
| 2 (double-digit blow-up hole) | 100 px | 160 px | 164 px |

At the old padding (20 px), the double-digit case left only 160 px against the new
162 px label — a 2 px overlap between the label and the big digit. I raised this to the
coordinator before changing the wording or the digit; the coordinator's direction was
to recover the deficit from the row's own left padding rather than touch the label
(the owner's deliberate wording) or make the label reshape itself as the counter
crosses from one digit to two (which would repeat the two-independent-derivations shape
that caused the item-1 bug). `padding` in `drawCounters`
(`GolfScoringActivity.cpp:596`) is `minValue(16, rect.width/8)` (was `minValue(20,
...)`), applied uniformly to all three counter rows. Worst case now clears by 4 px
(164 px available vs. 162 px label) instead of overlapping by 2 px.
