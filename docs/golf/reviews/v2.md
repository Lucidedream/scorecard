## What is correct

**The v2 scoring model is right.** `putts` → `in100` → `out100`, `strokes` derived and
never stored. Carry works both directions: raising putts lifts `in100`, lowering `in100`
pulls putts down to the floor. Focus cycles in entry order. `seedGolfHoleAtPar` sets
`putts=2, in100=2, out100=par-2`, reconstructing par exactly.

The `blocked`/`blockingFields` machinery from v1 is gone, and that is correct rather than
a regression: in v2 the constraint is maintained by moving the other field, so there is
no refusal state left to report.

**Entered-holes-only survived the rewrite.** `isEntered` is now
`golfHoleScore != 0` i.e. `in100 + out100 != 0`, and it still guards every sum. This was
the highest-risk part of the change and it is correct.

**v1 files are rejected, not migrated** — `"Rejected v1 state: in100 semantics changed
in v2"`. Exactly right: `in100` changed meaning, so a silent migration would misreport
old rounds.

Also correct: date removed from setup, sequence-based `round-NNNN-<slug>.json`
filenames, app renamed to *Scorecard*, menu row moved to the top, a real 32×32 icon,
and a new par-free round mode (`golfHasPar`) that scores without to-par when pars are
unknown — a genuinely good addition nobody asked for.

## Defect 1 — WITHDRAWN ENTIRELY. The data was correct; the defect was mine.

`src/golf/CourseStore.cpp:19-31` ships **Sanyang Golf Club with invented hole-by-hole
par and yardages.**

Only three facts about Sanyang were ever verified: 18 holes, par 72, ~7022 yards. The
per-hole sequence was never obtainable — the course databases are CAPTCHA-gated. The
baked-in par array sums to 72, which looks right, but the individual holes are guesses.

The yardages give the fabrication away: they total **6466 yards** against the verified
**7022**. They are wrong by 556 yards, so they cannot have come from a real card.

This is precisely the failure mode refused earlier and documented in
`docs/golf/examples/README.md`:

> Had I filled in a plausible-looking par sequence instead, the file would load silently
> and your to-par would be quietly wrong on every hole I guessed incorrectly.

It is now worse than a bad SD file: it is in flash, it looks authoritative, and it
cannot be corrected without a rebuild. A wrong par on any hole silently corrupts to-par
for every round ever played there.

### FINAL correction (2026-08-29, after the owner supplied the scorecard)

The owner produced the actual Sanyang scorecard. **Every number codex originally
shipped was correct** — Blue yardages, White yardages, par, and all four of its
`static_assert` totals match the card exactly:

| | Out | In | Total |
| --- | --- | --- | --- |
| Par | 36 | 36 | **72** |
| Blue | 3,196 | 3,270 | **6,466** |
| White | 2,910 | 3,043 | **5,953** |

Nothing was fabricated. I deleted real, correct, two-tee data and the
`applyBuiltInTeeYardages` mechanism that served it, on evidence that was simply wrong.

**How the error compounded.** My "proof" was a web-sourced 7,022-yard total that the
built-in contradicted by 556 yards. That figure does not describe this card at all. I
treated a single unverified number as decisive against a full internally-consistent
dataset — when the data itself carried the check that would have exonerated it:
codex's own `static_assert`s encoded per-nine totals that match the card. **The
verification I demanded of the data was already in the data.** I did not run it.

Then, told my premise was wrong, I reached for a second source (the owner's prose
strategy guide, 6,477) and treated *that* as authoritative over the scorecard — wrong
again, in the same shape, because a strategy guide's approximate distances are not a
card.

### Superseded intermediate correction



The owner had compiled a full Blue-tee course guide at
`~/.openclaw/workspace/memory/sanyang_course_guide.md` and given it to codex directly
during the rate-limit period. Checking codex's array against that guide:

* **The par array was byte-for-byte identical to the real card.** It was never
  fabricated. Calling it so was wrong.
* **The yardages were genuinely wrong** — 6466 total against a real Blue-tee 6477, with
  individual holes off by up to 18 yards. Those were approximations.

**Why I got it wrong.** My evidence was a web-sourced "7022 yards" total that the
baked-in yardages contradicted by 556. But 7022 is the *championship/back* tee; Blue
measures 6477. I compared against the wrong tee, concluded the whole entry was invented,
and generalised from the bad yardages to the good pars.

The removal was still net-correct — the yardages had to go, and shipping par-free was
safe rather than wrong — but the reasoning was faulty and the par data was lost for a
while as a result. The real data is now restored from source in
`docs/golf/examples/sanyang-suzhou.json`, self-consistency verified: front 36 / back 36
/ par 72, front 3173 / back 3304 / 6477 yards matching the guide's own stated totals,
and a stroke index that is a clean 1–18 permutation with the conventional odd-front /
even-back split.

**The lesson, and it is the third instance of the same error.** I twice before filed a
defect without checking a cheap fact — `ConfirmationActivity.h` existed upstream, and
the RoundedRaff path was unreachable. Here I had *contradicting* evidence and treated it
as decisive without asking which tee it described. Before calling data fabricated, check
whether the disagreement is explained by a different variant of the same measurement.
Ask the owner what he has; he had a full course guide the whole time.

**Original fix (superseded):** ship Sanyang par-free (`par` all zero, `hasYards=false`), which the new
`golfHasPar` path already supports — the owner scores normally and simply gets no to-par
until he enters the real card from the pro shop. `Practice 9` is fine because it is
plainly generic; Pebble Beach is fine because its pars are verified and it correctly
ships without yardages.

## Defect 2 — WITHDRAWN. This was a false positive by the architect.

`HomeActivity` render and dispatch disagree about where the Scorecard row sits.

* `render()` (line 350): `scorecardIndex = homeContinueReadingInMenu && !recentBooks.empty() ? 1 : 0`
* `loop()` (line 195): dispatches Scorecard at `menuIndex == 0`, unconditionally

They agree only when the condition is false. `RoundedRaffTheme.h:48` sets
`homeContinueReadingInMenu = true`, so on that theme with any recent book:

* selecting **Continue Reading** opens Scorecard
* selecting **Scorecard** opens File Browser
* every row below is shifted by one

Not seen in testing because Lyra and the base theme both set the flag `false`.

### Why it was wrong

The reasoning above silently assumed `recentBooks.size()` could exceed 1 while
`homeContinueReadingInMenu` is true. **No theme configures that combination.** The
worker checked and the matrix is:

| Theme | `homeContinueReadingInMenu` | `homeRecentBooksCount` |
| --- | --- | --- |
| BaseTheme | false | 1 |
| Lyra | false | 1 |
| Lyra3Covers | false (inherited) | 3 |
| RoundedRaff | **true** | **1** |

With RoundedRaff's single recent book, selector 0 is consumed by the recent-book branch
(which *is* "continue reading" — it opens `recentBooks[0]`), and Scorecard's selector 1
normalizes to `1 - 1 = 0`, matching the dispatch. Every other theme has the flag false,
where `scorecardIndex` is 0 and the subtraction is the identity. **The pre-fix code was
correct in every reachable configuration.**

I reasoned from the render/dispatch expressions in isolation and never checked whether
the divergent case was reachable. The worker verified it against the theme table and
pushed back rather than complying — which is what I have repeatedly asked for, and it
was right to do so here.

### What was kept anyway

The single-source `getScorecardMenuIndex()` helper was applied regardless, because the
original code genuinely did use two different coordinate systems for the same row and
was easy to misread — as I demonstrated. The refactor removes that fragility without
changing any correct behaviour. Net positive, wrong justification.

### The lesson

**Before filing a defect from code reading, check that the triggering state is
reachable.** A divergence between two expressions is only a bug if some real
configuration produces the divergent input. I have now made the mirror-image of this
mistake twice: earlier I called `ConfirmationActivity.h` invented without checking it
existed upstream, and here I called a code path broken without checking it was
reachable. Both times the fix was one grep away.

## A pre-existing upstream quirk, deliberately NOT fixed

While tracing Defect 2 I found that `activateSelection`'s cover-tile early return

```cpp
if (selectorIndex < recentBooks.size()) { onSelectBook(...); return; }
```

treats `selectorIndex` as a **book index**, while under `homeContinueReadingInMenu`
every other site treats it as a **menu row index** — the render highlight
(`HomeActivity.cpp:371`) and the navigation bounds (`:284-295`) both do. On RoundedRaff
with two or more recent books those two readings disagree and menu rows in that range
mis-activate.

`git diff upstream/develop` confirms this early return is **unchanged from upstream**.
It is a pre-existing upstream inconsistency that the golf work inherits, not one it
introduced; the Scorecard row simply happens to land in the affected range on that one
theme.

**Ruled: do not fix.** It is upstream behaviour; fixing it would deepen our
`HomeActivity.cpp` diff and raise rebase conflict surface; the owner's themes (Lyra and
the base theme) both set the flag `false`, so it never fires for him; and a fork
silently changing upstream navigation semantics is worse than a documented known quirk.
Revisit only if the owner switches to RoundedRaff and hits it.
