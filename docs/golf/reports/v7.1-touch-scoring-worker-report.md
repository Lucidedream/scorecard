# v7.1 touch scoring worker report

## Result

Touch boards can now count from the selected scoring row and jump directly to a hole from
a bottom sheet. The constexpr counter classifier assigns the left, centre, and right thirds
and rejects points outside the row (`src/activities/golf/GolfUiLayout.h:224-235`). The scoring
tap path still selects an unfocused row without counting; only a second tap on the selected
row dispatches decrement/removal or increment, and the centre remains inert
(`src/activities/golf/GolfScoringActivity.cpp:736-765`). Footer handling remains earlier in
the loop, so a footer tap cannot reach either body feature.

The constexpr hole-sheet layout, two-page rule, and bounded cell hit-test are at
`src/activities/golf/GolfUiLayout.h:237-277`. The sheet opens on the current page, checks Back
before side-key/swipe paging, cancels outside taps, and routes valid cells to the jump wrapper
(`src/activities/golf/GolfScoringActivity.cpp:321-410`). The wrapper follows the existing turn
change persistence sequence: under `RenderLock` it resets turn UI only after a real change,
then marks dirty, flushes because the hole changed, and requests a refresh
(`src/activities/golf/GolfScoringActivity.cpp:342-360`). The rules function changes only
`currentHole` and rejects the current or an out-of-range hole
(`src/golf/GolfRules.cpp:167-170`).

The sheet reuses the existing nine-cell score renderer, including unscored dots, penalty-mark
superscripts, and current-hole inversion (`src/activities/golf/GolfScoringActivity.cpp:1013-1053`).
Its translated Hole title, numeric page range, 72-pixel cells, and Back-only footer are drawn at
`src/activities/golf/GolfScoringActivity.cpp:1146-1170`. All added geometry and input state is
constexpr, automatic, or embedded in the existing heap-owned activity; no heap allocation was
added. The activity gained only a boolean and a page byte of persistent state.

## §38.3 acceptance

1. Both requested firmware environments compiled and linked successfully without a warning in
   either build output. Sizes are recorded below.
2. All 543 host tests passed. Counter-zone boundary/outside coverage is at
   `test/golf_layout/test_golf_layout.cpp:165-178`; strip tiling, centre round trips, page counts,
   and inert final-page cells are at `test/golf_layout/test_golf_layout.cpp:180-210`; jump
   isolation and invalid/current-hole rejection are at `test/golf_rules/GolfRulesTest.cpp:256-278`.
3. The new body path can only receive `FooterInput::hasTap()`, which is populated only after the
   existing runtime `mappedInput.hasTouch()` gate, and opening the strip additionally checks
   `mappedInput.hasTouch()` (`src/activities/golf/GolfScoringActivity.cpp:736-745`). With no touch,
   neither feature runs and the existing button paths continue unchanged.
4. This task changed no upstream file and added no translation key. The required main-branch scope
   command reports only the pre-existing `platformio.ini` X4 Pro profile (20 inserted lines),
   which is not part of commits `b18ca8d`, `d9de80c`, or `fd3753b`.
5. Every consumed tap returns from the loop: opening the strip returns before counter testing,
   selecting an unfocused row returns without counting, selected-row actions return after one
   dispatch, and the open sheet owns the entire loop (`src/activities/golf/GolfScoringActivity.cpp:681-688,736-765`).
   The existing long-press classifier remains distinct from the tap snapshot.

## Not verified without a device

No X4 Pro hardware was available. The owner still needs to verify that one tap produces one
visible count step; the centre third is inert; a first tap only focuses another row; all three
rows behave identically; the hole band opens on the current page; left/right swipes and Up/Down
page without wrapping; Back edge-swipe wins over paging; empty cells are inert; current/other
hole taps close correctly; and sheet open/close refreshes look clean on e-ink. The builds and
host tests establish compile/link compatibility, static geometry, rules isolation, and reported
static memory sizes, but they cannot prove physical touch calibration, gesture classification,
display appearance, SD flush behavior, or runtime heap high-water marks. Device verification
should watch the serial log and `ESP.getFreeHeap()` before entering Scoring, while opening and
closing both sheets, after several jumps, and after returning Home.
